0Summary

One frontend team, two products. Surface 1 is a daily-use procurement app for buyers, suppliers and approvers in India, Vietnam and China on 8 GB laptops over VPN. Surface 2 is a 3D layout editor that runs inside another company's application on integrated graphics. The design optimises for the same things in both: fast on a slow network, never losing work, equally good in three languages and without a mouse, and safe at the boundaries it does not own.

≤ 2.5 s
first useful screen on 10 Mbps VPN · budgeted at ~1.9 s; Part B's first download is 34 KB
60 fps
500 items at 1080p on Intel Iris Xe in Part B, with 15 draw calls (budget: ≥ 50 fps, < 300 calls)
4.8 ms
clearance check for 2,000 items (spatial hash; 342 ms brute force)
40 MB → ≤ 0.65 MB

The seven decisions that shape everything

DecisionWhy
One Nx monorepo, versioned shared packagesBoth surfaces build on @cloudworx/ui, tokens, i18n and API types, published with semantic versions. Each app pins its versions and deploys alone: shared code, separate release trains.
The server owns the data, the client caches itTanStack Query is the client's single copy of server data. REST loads it, the WebSocket keeps it fresh, optimistic updates make it feel instant, and Zustand holds only small UI state.
Big grids stay on the serverAG Grid's server-side row model asks for 100-row blocks; filtering, sorting, search and bulk actions run on the server, so 200,000 rows cost the browser about the same as 2,000.
Nothing is lost on a flaky VPNDrafts go to IndexedDB at once and autosave to the server; retries carry idempotency keys; the WebSocket resumes from its last sequence number; the UI says clearly when it is offline.
Surface 2 lives in an iframe behind a typed contractThe host keeps sign-in and navigation; the editor gets context and a short-lived token over an origin-checked postMessage contract, and takes the host's look from its brand tokens.
Every edit is a command3D drags, panel edits, keyboard shortcuts and accepted AI proposals all become the same undoable commands in one store, so the 3D view, list and properties never disagree.
3D cost is fixed by design, not by luckCAD models go through a pipeline (3 LODs, Meshopt, KTX2, per-model budgets) and are drawn with instancing, so draw calls grow with the number of distinct models, not items.

3Application structure

How the two surfaces share a design system, tokens and components without sharing one release train, and where the module boundaries are.

3.1 One repository, separately versioned packages

cloudworx-frontend/                Nx + pnpm workspaces
├── packages/                      SHARED · published with semantic versions
│   ├── tokens/        1.4.0       design tokens → CSS variables
│   ├── ui/            2.3.0       React components (React Aria + CSS Modules)
│   ├── i18n/          1.1.0       i18next setup, ICU, Intl formatters, locale resolver
│   ├── api-types/     3.0.0       types generated from the OpenAPI specs
│   └── host-bridge/   1.0.0       typed postMessage contract (Surface 2 and test host)
├── apps/                          PRODUCTS · each deployed on its own
│   ├── procurement/               Surface 1
│   ├── configurator/              Surface 2 (embedded)
│   └── test-host/                 stands in for the host page in CI and staging
└── tooling/                       shared lint, TypeScript and test configs

One repository makes cross-cutting changes (a token and the component that uses it) a single reviewed change. Publishing the packages with versions keeps the releases separate.

3.2 How sharing works without a shared release train

  1. A change to packages/ui merges with a changeset describing it as a patch, minor or major change.
  2. CI publishes the new version (for example @cloudworx/ui@2.4.0) to the private registry with a changelog.
  3. Each app pins the versions it uses. Surface 1 can take 2.4.0 this week while Surface 2 stays on 2.1.0 mid-release; nothing breaks for an app that did not opt in.
  4. Nx affected builds, tests and deploys only the apps whose code or pinned versions changed. 3D models have their own pipeline (§9).
Within the monorepo, apps consume packages through pinned published versions, not live workspace links, in release builds. Developers can link locally to try an unreleased change, but CI builds exactly what will ship.

Tokens are authored in Figma (Tokens Studio), exported as JSON and compiled by Style Dictionary into CSS variables and TypeScript constants. Components are styled with CSS Modules (scoped, zero runtime), read only semantic variables, and use CSS logical properties, so a right-to-left language later needs no redesign. Part B's src/design-system/ is a small working version of this package.

3.4 Module boundaries

Rule 1 · Dependencies point one way

Apps → packages → tokens. Packages never import apps; apps never import each other. Enforced by Nx module-boundary lint rules.

Rule 2 · Each module has one front door

Every package and feature exports a public index.ts. Deep imports into another module's internals are lint errors.

Rule 3 · Shared means generic

A component enters packages/ui only when both products need it and it carries no business meaning. The supplier grid and the 3D viewport stay in their apps.

Rule 4 · The domain has no UI imports

In Surface 2, domain/ (commands, snapping, rules, BOM) imports neither React nor three.js, so it is unit-tested in isolation and can move into a web worker or onto the server unchanged.

LayerSurface 1 · apps/procurementSurface 2 · apps/configurator
app/Shell, router, providers, runtime config, error boundariesHost bridge, theme adapter, error boundary with a WebGL fallback
features/One folder per screen familyPanels: palette, items, properties, rule check, BOM, assistant
domain/(none: rules live on the server)Layout model, commands and history, snapping, clearance rule, BOM
state/ / data/Query keys, API client, realtime client, drafts, uploadsLayout store, API client, realtime client, proposal state

Rejected: separate repositories (versions drift, cross-cutting changes need several pull requests); one app for both surfaces (one release train, and the host would load procurement code); sharing the design system at runtime with Module Federation (a library change could break a live app that never released); copying components into each app (copies drift, every fix made twice).

4.2 Server state and caching

  • Query keys mirror the API: ['tasks', {status}], ['rfq', id], ['rfq', id, 'quotes']. Invalidating a prefix refreshes everything beneath it.
  • Freshness per kind of data: reference data is fresh for 24 h, lists for 30 s; the open record revalidates on focus and reconnect.
  • Screen-shaped endpoints: the BFF serves the home page in one call, saving three VPN round trips on the most important screen.
  • Bounded memory: unused queries are collected after 5 minutes; the persisted cache (inbox and home only) is cleared at sign-out and never used on shared VDI profiles.

4.3 Optimistic updates, done safely

Approve task  →  remove it from the cached list immediately          (feels instant)
              →  POST /tasks/{id}/approve   Idempotency-Key: 7f3c…   If-Match: "v4"
   200        →  invalidate ['tasks'] and ['rfq', id]                 (resync counts)
   412/409    →  restore the task, show "Already approved by Wei L." (no silent double action)
   network    →  restore the task, mark it "Not sent · Retry"
  • Idempotency keys make retries safe; ETags with If-Match catch concurrent edits.
  • Optimism is used where rollback is cheap and visible (approvals, task actions, comments, 3D edits). Irreversible commands (award, submit onboarding) wait for the server.

4.4 Autosave and drafts on long forms

WhenWhat happens

4.5 Live updates over WebSocket

  • One connection per tab, opened after the shell renders. Screens subscribe to topics (tasks:me, rfq:2041, layout:er-104) and unsubscribe when they unmount.
  • Every event has a sequence number. On reconnect the client sends its last seq and the server replays a 15-minute buffer; for a larger gap it sends resync and the client invalidates the active screen.
  • Events update the cache, never components directly; handlers are idempotent by seq. New inbox items never shift the list under the cursor: a "1 new task" pill lets the user choose.
  • Heartbeat every 25 s; reconnect with exponential backoff (1 s → 30 s) plus jitter, so thousands of clients do not reconnect at once after a VPN gateway restart.

4.6 Behaviour on a flaky VPN

6.2 Text expansion, CJK and locale formats

Text expansion

Vietnamese runs about 30–40% longer than English. No fixed widths; buttons and tabs grow, labels wrap, grid cells truncate with a tooltip. A pseudo-locale in CI screenshots catches overflow and untranslated text.

CJK line breaking

Under :lang(zh-CN): line-break: strict (no line starts with 。or ，), word-break: normal, overflow-wrap: anywhere for long part codes, no fake italics. Noto Sans SC loads only for Chinese, subset, with font-display: swap.

6.3 Accessibility approach (WCAG 2.2 AA)

  • Accessible by construction: React Aria for interactive components; semantic HTML elsewhere.
  • Visible focus, a skip link, logical tab order, focus moved into dialogs and back, targets at least 24 × 24 px (44 px on mobile).
  • One announcer (a polite live region) for asynchronous events: "Draft saved", "New task", "Undone: move D-01".
  • Never colour alone: statuses carry text or an icon; violating 3D items are red and listed with a warning icon and a message.
  • The 3D view has a text twin: the placed-items list, properties and rule-check panels expose the whole scene to a screen reader.
  • Tested continuously: axe fails the build; keyboard paths below are scripted in Playwright; NVDA + Edge and TalkBack checks before each release.

7Embedding in the host

Iframe or micro-frontend and why, the postMessage contract (context hand-off, token refresh, resize, navigation, errors), origin checks, CSP and cookie constraints, and matching the host design language.

7.1 Iframe, with a micro-frontend fallback

Iframe (chosen)Micro-frontend
IsolationSeparate JavaScript, CSS and memoryShares the host page; CSS and globals can clash
If the 3D view failsOnly the frame is affected; the host keeps workingA WebGL crash or a 1 GB heap can freeze the host's sales app
Releases and React versionFully independentCoupled to the host's runtime and shared dependencies

Why iframe: the editor is the heaviest thing on the page (up to 1 GB, WebGL), it belongs to a different company, and it must ship on its own schedule. Fallback if a host forbids iframes: the same app as a web component in Shadow DOM, loaded with Module Federation, speaking the same contract over DOM CustomEvents. Only the transport changes, inside packages/host-bridge.

7.3 Token handling

  • The host owns sign-in (OIDC). The editor never sees a password and never runs its own login.
  • The access token is short-lived (≈ 15 min), audience-scoped to the Configurator API, kept in memory only: never in the URL, storage or logs.
  • On a 401 the API client pauses its queue, requests a token, and replays; a second failure sends app:error AUTH_FAILED so the host can re-authenticate.
  • The Configurator API validates issuer, audience, expiry and signature on every call; the browser is never trusted for permissions.

7.4 Resize, navigation and errors

ConcernApproach
ResizeDefault: the host gives the frame a full panel and the editor fills it, adapting its layout. Optional: a ResizeObserver reports content height (throttled to one message per frame). Dialogs and menus are designed to stay inside the frame; full screen uses allow="fullscreen".
NavigationInside the editor: an in-memory router, not the host's URL. Leaving the editor: app:navigate, and the host decides. Deep links arrive in host:init or host:navigate.
ErrorsHOST_TIMEOUT, AUTH_FAILED, LAYOUT_NOT_FOUND, WEBGL_UNAVAILABLE (the editor falls back to its list and BOM view), ASSET_LOAD_FAILED (retry with backoff). Each side shows the code in its own language and style.

7.5 Origin checks

const ALLOWED_HOSTS = runtimeConfig.allowedHostOrigins;     // exact origins, per environment

addEventListener('message', (e) => {
  if (!ALLOWED_HOSTS.includes(e.origin)) return;            // 1. the right website?
  if (e.source !== window.parent) return;                   // 2. from our actual parent?
  const msg = MessageSchema.safeParse(e.data);              // 3. the right shape?
  if (!msg.success || msg.data.protocol !== 'cwx-embed') return;
  handle(msg.data);
});
window.parent.postMessage(message, hostOrigin);             // never '*', so the token cannot leak

The host applies the same three checks to messages from the iframe. Exact origin comparison (not "contains hostcorp"), and the allowed list comes from runtime configuration so each environment (test host, staging, production) has its own.

  img-src 'self' blob: data: https://assets.configurator…;

  • On the host: frame-src https://configurator…, and the iframe with sandbox="allow-scripts allow-same-origin allow-forms allow-downloads", allow="fullscreen; clipboard-write" and a title for screen readers.
  • Cookies: inside another company's page our cookies are third-party, and Chrome/Edge restrict them. The design uses no cookies for auth: the bearer token from the host. If a cookie is ever needed: SameSite=None; Secure; Partitioned (CHIPS), or serve the editor from a host subdomain to make it same-site.
  • Storage is partitioned per host as well, which is fine: the Cache API and IndexedDB still cache models and the manifest, just separately for each host.

7.7 Matching the host design language

host:init → theme: { "color-primary": "#c8102e", "font-family": "Host Sans",
                     "radius": "2px", "density": "compact", "mode": "light" }
  1. The theme adapter validates each value (real colours, known lengths, an allowed font list), so a host cannot inject arbitrary CSS.
  2. It maps them onto our brand and semantic tokens (§3.3); every component re-styles at once, with no code change.
  3. It checks contrast: if the host's colour fails WCAG AA on our surfaces, it uses the nearest passing shade.
  4. Missing values fall back to our defaults; host:theme applies changes live (e.g. dark mode).

The host controls colour, font, radius, density and mode. We keep the editor's layout, the 3D visuals and accessibility.

8The 3D editing workspace

Scene structure, selection and transform editing, snapping, undo and redo, showing rule violations, and keeping the 3D view in sync with the list and property panels. This section describes what Part B implements, then how it scales to 2,000 items.

8.1 Scene structure

<Canvas>                                    React Three Fiber, rendered on demand
├─ Static       floor plane · 0.5 m grid · walls                    a handful of draw calls
├─ Items        one InstancedMesh per model × material × LOD         per-instance matrix + status colour
├─ Overlays     selection outline · 0.6 m clearance zone · violation links · AI ghost layer
│               (never raycast, so clicks always reach the floor and items)
├─ Labels       HTML label for the selected item only
└─ Camera       orbit / pan / zoom, fitted to the room on resize

The domain works in metres from the room's north-west corner; the scene converts to centred world coordinates. The layout is the single source of truth: the scene is a pure function of the store, so nothing in three.js has to be kept in sync by hand.

8.2 Selection and transform editing

  • Picking: instanced meshes report instanceId. At 2,000 items picking uses the same spatial hash as the rule check: the floor point under the pointer finds the item whose footprint contains it in O(1), instead of ray-testing every triangle.
  • Move: items move on the floor plane (equipment does not float), with pointer capture so a fast drag never "drops" the item. The drag preview lives in local state; one command is committed on release.
  • Rotate: 90° steps (R), re-snapped so the turned footprint stays on the grid and on the floor.
  • Properties: position (as the north-west corner, always a clean grid value), rotation and label; edits commit on Enter or blur, one undo step each.
  • Keyboard: list navigation, R, Delete, Ctrl+Z/Y; arrow keys nudge one cell (§6.4).

8.3 Snapping to the grid

The north-west corner of the rotated footprint snaps to the nearest 0.5 m line and is clamped so the whole footprint stays on the 20 × 12 m floor. A quarter turn swaps width and depth before snapping. Floating-point noise is rounded at millimetre precision. Unit-tested in Part B.

8.4 Undo and redo: every edit is a command

type Command = { kind: 'add' | 'remove' | 'move' | 'rotate' | 'update' | 'batch';
                 target: string;                    // "C-03", for messages and announcements
                 apply(layout): Layout; revert(layout): Layout };
  • Exact restore: commands store previous values, so undo returns the exact position and even the item's place in the list.
  • Batches: loading a layout or accepting an AI proposal is one command, so one Ctrl+Z reverts it.
  • No-ops are dropped: a drag that ends where it started records nothing. History is capped at 200 steps.
  • Same commands to the server: each committed command is sent as an operation with the layout version (POST /layouts/{id}/ops, If-Match). The server re-runs the rules authoritatively; on a version conflict, operations on different items rebase, otherwise the layout reloads with a message.

8.5 Showing rule violations

  • Rule: any two items closer than 0.6 m edge to edge (footprint to footprint), overlaps included.
  • Speed: a spatial hash compares each item only with items in neighbouring cells. Measured: 4.8 ms for 2,000 items in a realistic layout, against 342 ms for all pairs, so it runs on every drag move. Denser future rules (door swing, cable length) move to a web worker; the domain has no UI imports, so that is a move, not a rewrite.
  • Live feedback: the check runs on the drag preview and the placement ghost, so a conflict shows before the user commits.
  • Display: red items in 3D (per-instance colour), a warning icon in the list, and a message naming both items in the rule panel ("C-03 and D-07 are 0.4 m apart"); clicking it selects the item. The live region announces new conflicts.

8.6 Keeping the 3D view, list and properties in sync

One Zustand store holds the layout, the selection and any AI proposal. The 3D view, the placed-items list, the properties panel and the rule panel are all readers of the same store, and selection is a store field, so selecting in the list highlights in 3D and the list scrolls to an item picked in 3D. Derived data (violations, BOM) is computed once per layout change and shared. At 2,000 rows the list is virtualised (TanStack Virtual); Part B's 500 rows use content-visibility.

From a raw 40 MB CAD export to a web-ready model: simplification and levels of detail, Meshopt compression, KTX2 textures, instancing, culling, lazy loading and caching, with target numbers per model and per scene.

9.4 At runtime

  • Instancing: one InstancedMesh per model × material × LOD. Each frame the camera moved, instances are re-bucketed by distance (throttled), and per-instance frustum tests skip off-screen items: 2,000 sphere tests cost well under a millisecond. Part B proves the principle: 9 draw calls for all items whatever their number, 15 in total at 500 items.
  • Decoding off the main thread: the Meshopt decoder and the KTX2 (Basis) transcoder are WebAssembly in web workers, so loading never stutters the editor (CSP allows 'wasm-unsafe-eval').
  • Lazy loading: the manifest loads with the layout; a model downloads on first use; placeholders (the footprint box, as in Part B) show instantly.
  • Caching: content-hashed URLs, long immutable CDN caching, and the Cache API in the browser, so the second visit is close to zero bytes.

Rejected

  • Draco instead of Meshopt: comparable compression, but slower decoding on weak CPUs, a larger decoder, and it does not compress animation or instance data. Meshopt also pairs with quantisation and is three.js's default path.
  • PNG/JPEG textures: they expand to full size in GPU memory; KTX2 stays compressed.
  • Simplifying at runtime: CPU cost on every load on the weakest machines; done once in CI instead.
  • One mesh per item: 2,000+ draw calls. Merging the room into one static mesh: few draw calls, but every edit would rebuild it.

10AI assistant panel

Streaming replies, previewing the agent's proposed change in the 3D view before the user accepts it, and undoing an accepted change. The mechanism is shared by both surfaces.

10.1 How a reply streams

1  POST /assistant/messages  { conversationId, text, context }      REST    → 202 { runId }
2  WS   assistant.delta  { runId, text: "C-03 is 0.4 m from D-07…" } WSS     (many, in order by seq)
3  WS   assistant.done   { runId, sources, proposal? }
   Stop → POST /assistant/runs/{runId}/cancel                          REST
  • Only REST and the existing WebSocket, the two channels the brief fixes; reconnect and replay (§4.5) also protect a reply in progress.
  • Tokens render as they arrive; the finished reply, not each token, goes to the live region.
  • The client sends references (screen, layout id and version, selection, violation ids), never data; the server resolves them with the user's own permissions. Content is treated as data, not instructions; the LLM is called only server-side.

10.2 A proposal is a set of commands

proposal: { layoutVersion: 41,
            summary: "Move C-03 0.5 m east to clear D-07",
            changes: [ { op: "move", itemId: "c03", x: 4.9, z: 2.3 } ],
            resolves: [ "c03|d07" ] }

The agent never edits the layout. It returns the same operations the editor already understands (§8.4), so the client can validate them with its own rules and the user stays in control. In Surface 1 the same pattern previews proposed actions (for example a document request to 2 suppliers) and confirms them through the normal REST command with the user's own permissions.

10.3 Preview, accept, undo

StepBehaviour
ValidateThe client checks the items exist, snaps positions, applies the changes to a copy of the layout and runs the clearance rule on it: "resolves 1 issue · creates 0". New violations are shown, not hidden
PreviewA ghost layer draws moved items translucent at their new place, with a dashed arrow from the old position; originals are dimmed. Nothing in the real layout changes. The same change is listed in text for screen-reader users
AcceptThe changes apply as one batch command ("Assistant: move C-03"), go to the server as operations with the version, and announce "Done: assistant fix"
StaleIf the layout version moved on since the proposal, it is re-validated; if it no longer applies cleanly it is marked stale with "Ask again"
Reject / undoReject removes the ghost layer. After accepting, one Ctrl+Z reverts the whole fix like any other edit; the server keeps the operation log for audit
